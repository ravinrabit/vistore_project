VISTORE - ETAPA 5: EXTRAS
Explicação para a apresentação
======================================================================

1. O QUE FOI FEITO
----------------------------------------------------------------------
- Preventivas (RN09): o gestor cadastra uma manutenção que se repete
  (ex.: limpar o ar-condicionado a cada 90 dias). O sistema cria a OS
  sozinho 7 dias antes da data prevista.
- QR Code por equipamento: uma etiqueta para imprimir e colar no
  equipamento. Quem aponta a câmera abre um chamado já com o equipamento
  e o local preenchidos.
- Alertas por e-mail: o técnico, o solicitante e o gestor recebem aviso
  nas mudanças que precisam da atenção deles.
- Gráficos: os painéis do gestor e do administrador mostram as ordens
  por status e os chamados abertos nas últimas 8 semanas.

3. DECISÕES IMPORTANTES (E COMO EXPLICAR NA BANCA)
----------------------------------------------------------------------

3.1 Preventivas (RN09)
    O comando "python manage.py gerar_preventivas" procura as preventivas
    ativas cuja próxima data está a 7 dias ou menos e, para cada uma:
    - cria a OS já "Aguardando atribuição" (Classificada), porque o tipo de
      serviço já é conhecido. É assim no fluxograma: a preventiva entra na
      etapa de classificação;
    - registra o responsável pela preventiva como solicitante;
    - empurra a próxima data em "periodicidade" dias.
    Como a data anda para frente, rodar o comando duas vezes no mesmo dia
    não cria OS repetida (há teste para isso).
    A OS guarda de qual preventiva veio (campo preventiva), e o detalhe
    mostra a etiqueta "Preventiva".
    Assim como o verificar_treinamentos, é agendado uma vez por dia no
    Agendador de Tarefas do Windows (ou cron no Linux).

3.2 QR Code
    O QR é desenhado no navegador pela biblioteca qrcodejs (via CDN), então
    o projeto não ganhou nenhuma dependência Python nova.
    Ele guarda o endereço /ordens/nova/?equipamento=<id>. A tela de abrir
    chamado lê esse parâmetro e preenche equipamento e local, mas só se o
    equipamento for da unidade de quem está logado. Se não for, ou se o
    parâmetro vier errado, o formulário abre vazio, sem erro (há testes).
    A página tem um botão de imprimir; o CSS de impressão esconde tudo
    menos a etiqueta.
    Observação: em localhost o QR aponta para o próprio computador. Ele só
    funciona no celular de outra pessoa quando o sistema estiver publicado.

3.3 Alertas por e-mail
    Quem recebe:
    - técnico: quando uma OS é atribuída a ele;
    - solicitante: quando o chamado é concluído (convite para avaliar);
    - gestores da unidade: incidente com lesão/afastamento (RN08);
    - gestores e o técnico: quando a OS volta para atribuição (RN03).
    Duas escolhas importantes:
    - transaction.on_commit: o e-mail só sai depois que a mudança foi
      gravada no banco. Se algo der errado e a gravação for desfeita, não
      sai e-mail falando de uma mudança que não aconteceu;
    - fail_silently=True: se o servidor de e-mail cair, a OS continua
      funcionando. O e-mail é um aviso, não uma regra de negócio.
    No desenvolvimento, o EMAIL_BACKEND é o de console: os e-mails aparecem
    no terminal do runserver. Em produção, basta trocar no .env (ver
    .env.example).

3.4 Gráficos
    Chart.js via CDN, sem framework. Escolhas:
    - cada gráfico tem uma série só e uma cor só. Nenhuma informação
      depende de distinguir cores, o que ajuda daltônicos;
    - a cor é um azul SENAC um pouco mais claro (#1f66b0), validado para
      contraste e luminosidade de gráfico;
    - cada gráfico tem "Ver os números em tabela", para leitores de tela e
      para quem prefere os números;
    - o gestor vê só a própria unidade; o administrador vê todas.
    Problema encontrado e resolvido: o filtro aberta_em__date do Django
    precisa das tabelas de fuso horário do MariaDB, que o MariaDB portátil
    não traz, e a contagem saía zero. A solução foi filtrar por um intervalo
    de data e hora (de segunda 00:00 até a segunda seguinte), que funciona
    em qualquer banco.

3.5 Uma correção de bônus
    O histórico ordenava só por data e hora. Quando duas mudanças são
    gravadas no mesmo instante (a preventiva cria a OS e já a classifica),
    a ordem ficava ambígua. Agora o id desempata (migração 0005).

6. PERGUNTAS QUE A BANCA PODE FAZER
----------------------------------------------------------------------
P: Por que a OS preventiva já nasce classificada?
R: Porque o tipo de serviço vem da preventiva. É o que o fluxograma mostra
   ("preventiva entra aqui 7 dias antes"). O gestor só precisa atribuir,
   e a RN01 continua valendo na atribuição.

P: E se o e-mail falhar?
R: A OS segue normalmente (fail_silently). E o e-mail nunca sai antes da
   gravação no banco (on_commit).

P: Por que não usar uma biblioteca Python para o QR Code?
R: Para não aumentar as dependências. O navegador desenha o QR com
   JavaScript, e o servidor só monta o endereço.
